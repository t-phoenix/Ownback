Ownback architecture

How the app, backend, contracts and partner protocols fit together, what infrastructure we run, and what each partner prize needs to see. Built to the 27-screen wireframes and PRD v2.

v3 · 6 Nov 2026Mainnet for money · Arkiv on testnetPartners: Arc · 0G · Arkiv
v3 (6 Nov): user decisions and security audit. The build-level specs now live in the repo (docs/, contracts/, backend/, database/, frontend/) and win over this page where they differ.
  • Buys. Every buy needs the user's signed BuyApproval, which the vault verifies; there's no automatic Sunday buy, only a reminder.
  • Fees. Fees are simulated and capped per user (default 5%).
  • Deposits. Auto-add uses a one-time-approved OwnbackDepositForwarder plus CCTP into vault.receiveDeposit.
  • Venues. Multi-chain venues, including BNB Chain (via an audited bridge, behind a flag).
  • Arkiv. SDK 1.0.1 schemas with lifetimes of at most about 182 days. Reads use createdBy + ownedBy our writer.
  • Addresses. All public contract addresses are verified from three sources (Arc chain ID 5042).

At a glance

A Next.js PWA talks to one backend (Next.js route handlers plus two scheduled workers). Users' dollars sit in their own wallets and in a vault contract on Arc. AI on 0G Private Computer reads receipts and Gmail invoices and works out who made the product and who supplies it. A public registry of brands, suppliers and verified token addresses lives on Arkiv, along with an anonymous proof record for every buy. When the user approves a buy, a keeper moves those jars from Arc to the cheapest venue across chains (Solana first, using CCTP) and buys the tokenized stock into the user's own address.

Gasless on every chain

Rule: users only ever hold dollars (USDC). They never need ETH, SOL or any other gas token, on any chain. Every network fee is either paid by us (sponsored) or taken in USDC from the amount being moved, and the app shows it in dollars before the user approves.

Who pays, and how it shows

  • Demo (hackathon): sponsor everything with Gas Station and Kora. Fund the Gas Station policy and the Kora fee payer with about $10. Every screen says "Network fee $0.00 (we cover it)".
  • After launch: keep sponsoring deposits and confirms; take the actual network cost of each buy in USDC from the batch (already shown as "fees $0.05" on Review and Done). Seed-phrase users on EVM pay through Circle Paymaster in USDC.
  • Limits so sponsorship can't be drained: a Gas Station policy with per-user daily caps and an allowlist of contracts (USDC, Gateway Wallet, OwnbackVault); Kora configured to sign only those program calls; rate limits on our relayer.

Verify before relying on it

  • Gas Station's chain list includes Arc mainnet (the docs table we read was cut off).
  • Circle Paymaster's fee: the docs say 10% of gas on Arbitrum and Base; check current pricing.
  • Whether the Gateway Wallet accepts a signed authorization deposit, so EOAs can deposit without gas. If not, seed-phrase users deposit on Arc or Solana, or use Paymaster.
  • Kora's current setup steps and whether the hackathon can use a hosted Kora node instead of running one.

Key flows

1 · Sign in

  1. Google: PWA → Circle Web SDK social login → Circle returns a user token. Backend creates (first time) an ARC SCA wallet and a SOL wallet for that user and stores both addresses.
  2. Seed phrase: PWA creates or imports 12/24 words, derives both addresses, keeps the encrypted words on the device and sends only the addresses plus a signed login message (SIWE-style) to the backend.
  3. Set your rules → backend calls nothing on-chain yet; the vault reads rules when the user first allocates.

2 · Deposit

  1. User picks the chain they're sending from; the app shows the EVM or Solana address.
  2. Arc deposits land directly. Other chains: the app asks the user to approve moving USDC into the Gateway Wallet (Gas Station pays EVM gas), giving one balance.
  3. When jars need dollars on Arc, the app mints from the Gateway balance on Arc and deposits into the vault in one signed step.

3 · Add a purchase (Gmail or camera)

  1. Gmail: scanner lists messages from a shop allowlist (Amazon, Flipkart, Myntra, Croma, Nykaa, Swiggy Instamart, Blinkit…) in the last 30 days, skips IDs already processed, and sends the text body to 0G (private mode). Bodies are dropped after extraction.
  2. Camera / upload / voice / typed: the image or audio goes straight to 0G; nothing is written to disk.
  3. 0G vision/LLM returns {shop, items[], total, currency, date, is_product} with a request ID.
  4. Backend fetches the FX rate for that date, converts to USD and saves rate, source and time with the purchase.
  5. Match: brand → maker (0G tool-calling model + Wikidata) → Arkiv company and asset lookups → supplier-of and materials from Arkiv → keep only assets with a verified token and a live Jupiter quote. Unknown or private brand → fallback screen.
  6. Split 70 / 20 / 10 across what's buyable, in whole cents; check the monthly limit (the only spend cap the vault checks).

4 · Confirm

  1. User taps "Confirm $47.75 across 6" → one Arc transaction: vault.allocate(purchaseId, assets[], amounts[]), signed in Circle's challenge (Google users) or locally (seed users).
  2. Vault checks limits, moves USDC from the user's free balance into the jars and emits Allocated. Backend mirrors it into Postgres and shows "Saved".

5 · Buy (user approves, keeper executes)

  1. Sunday reminder (or any time): Buy review quotes every enabled venue and picks the cheapest all-in route; reference price check (≤ 2%); fees vs the user's cap. The user signs a BuyApproval (typed data).
  2. Keeper (Circle developer wallet) calls vault.execute(batchId, domain, orders) with the signed approvals, which the vault verifies. The vault burns the total through CCTP to the fixed relay token account on Solana and records each user's share in Executed.
  3. Poll Circle's attestation; call receiveMessage on Solana to mint USDC to the relay.
  4. For each entry: Jupiter swap USDC → asset with output to the user's own token account (create the ATA if missing; relay pays rent and fees).
  5. Write one Arkiv proof per entry (asset, amount, tx hashes, 0G request ID; no address). Push "Buy done".
  6. If a swap fails, USDC stays in the relay and is retried next run; after two failures it is sent back to Arc and returned to that user's free balance.

6 · Withdraw and share

  1. Withdraw: vault.withdraw(amount) sends free USDC only to the caller. Shares never pass through us after the swap; they are already in the user's wallet.
  2. Share: /card/[id].png renders the card; the shared link /u/[code] shows it with the referral code and a sign-in button.

Vault contract (Arc)

// Sketch only. The frozen spec is contracts/vault-spec.md (v3): signed BuyApproval in execute,
// receiveDeposit from forwarders, no per-asset cap (Q1), 48 h Solana recipient change.
contract OwnbackVault {
  // per user
  struct Rules { uint16 rateBps; uint64 monthlyCap; bytes32 fallbackAsset; }
  mapping(address => Rules) public rules;               // rateBps must be 200..1000 (2–10%)
  mapping(address => uint256) public free;              // USDC not yet in a jar
  mapping(address => mapping(bytes32 => uint256)) public jar;   // asset id → USDC
  mapping(address => mapping(uint32 => uint256)) public spentInMonth;

  function setRules(Rules calldata r) external;           // checks bounds
  function deposit(uint256 amount) external;              // USDC transferFrom
  function allocate(bytes32 purchaseId, bytes32[] calldata assets, uint256[] calldata amounts) external;
      // reverts over monthly cap or max per asset; purchaseId can't be reused
  function cancelJar(bytes32 asset) external;             // jar → free
  function withdraw(uint256 amount) external;             // free → msg.sender only

  // keeper only
  function execute(bytes32 batchId, Entry[] calldata e) external onlyKeeper;
      // each entry: user, asset, amount ≤ jar, amount ≥ $5; burns total via CCTP
      // to the venue's fixed relay (set at deploy, changeable only after a 48 h timelock)
  event Allocated(address indexed user, bytes32 purchaseId, bytes32 asset, uint256 amount);
  event Executed(bytes32 indexed batchId, address indexed user, bytes32 asset, uint256 amount, uint32 domain);
}

Tests (in Studio, then Foundry): rate outside 2–10% reverts · allocation over the monthly cap reverts · the same purchase ID twice reverts · withdraw only ever pays the caller · execute below $5 or above the jar reverts · non-keeper execute reverts · relay change before the timelock reverts.

Security and trust

  • What Ownback can never do: move tokens out of a user's wallet, withdraw anyone's free USDC, or send jar money anywhere except the venue relay for that jar.
  • The one custody gap: for about a minute per buy batch, bought-to-be USDC sits in the relay on Solana between the CCTP mint and the swap. It is capped by the batch, logged per user on-chain, and proven on Arkiv. Post-hackathon fix: a small Solana program that swaps and enforces the destination.
  • Keys: users' keys are with Circle (Google users) or on their device (seed users). The keeper's Arc key is a Circle developer-controlled wallet. Only the Solana relay key and the Arkiv writer key live in our env vars, and both hold dust.
  • Token safety: every buy checks the mint against the Arkiv asset entry, which came from the issuer's official list; DexScreener shows fake PAXG/XAUt pools on Solana.
  • Privacy: images, audio and email bodies are processed in 0G private mode and not stored. Gmail access is read-only, asked for on tap, revocable, and limited to shop senders.
  • Rules: xStocks aren't for US persons, so geo-block US. No advice, no promise of returns; the user picks the rule, we execute it.
