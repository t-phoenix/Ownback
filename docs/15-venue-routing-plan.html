Plan · 23 Nov 2026 · proposal, nothing built yet

Best price across venues, without losing what works

Ownback buys every token through one route today: Jupiter's free swap API, with our relay paying gas. This plan keeps that route as the default and fallback, adds a small adapter layer so any aggregator or DEX can be plugged in, quotes the enabled ones side by side, and shows the user which one wins and why.

The short answer

An aggregator mostly suffices, but one is not enough. On Solana, Jupiter already routes through Raydium, Orca, Meteora and the other pools where xStocks and Ondo tokens trade, so adding single DEXs one by one would add little. What it can't do for us is race the other big routers (DFlow, OKX) or the RFQ market makers while our relay pays the gas: Jupiter's meta-aggregator turns DFlow and OKX off whenever the fee payer isn't the trader.

So: build a venue adapter layer; keep today's Jupiter connection as adapter #1; add Jupiter's new Router API and DFlow next (both let our relay pay gas and both support our fee); try Jupiter's RFQ path (JupiterZ) for larger orders; leave OKX until its docs and terms are confirmed.

Three ways to grow

A · Switch to Jupiter's meta-aggregator

One integration races four routers.

But with our relay paying gas, DFlow and OKX drop out, the fee becomes a referral split, and Jupiter executes the trade, so our signer checks change. Gains less than it looks.

B · Venue adapters, best of N Recommended

A small interface every venue implements. Quote the enabled ones in parallel within a time budget, keep the best net tokens out, fall back to Jupiter.

Keeps the relay, our fee and our transaction checks the same for every venue. Each new venue is one file plus a flag.

C · Third-party meta-aggregator

Hand routing to OpenOcean or similar.

Access is whitelisted, it adds a dependency between us and the user's trade, and gas sponsorship isn't documented. No.

How it fits together

One router picks the venue for each token buy or sell. Every adapter answers the same three questions: what would you give us, build me the transaction, and are you healthy. The rest of the app stays venue-blind.

The adapter contract

type VenueId = 'jupiter_v1' | 'jupiter_v2' | 'dflow' | 'jupiter_rfq'

interface Venue {
  id: VenueId
  label: string            // "Jupiter", "DFlow"
  kind: 'aggregator' | 'dex' | 'rfq'
  can: { payer: boolean; platformFee: boolean; token2022: boolean }
  quote(q: { inMint; outMint; amountRaw; feeBps }): Promise<VenueQuote | null>
  build(quote, { owner, payer, feeAccount }): Promise<{ txBase64 }>
  health(): VenueHealth   // last ok, error rate, p50 ms
}

Rules that keep it safe

  • Rank by net tokens out after every fee, never by the venue's own price.
  • A venue is used only if its adapter supports a relay payer and our fee (can).
  • Every built transaction passes the same check as today: the relay is the fee payer, the user is the only other signer, and the output lands in the user's own account.
  • Simulate before asking for a signature: tokens out must be at least the minimum shown.
  • A venue that times out or errors is skipped for this quote and marked unhealthy for 60 s. Jupiter v1 is always tried.
  • Each venue has its own flag (VENUE_DFLOW=1), so one can be turned off without a deploy of code.

What gets stored

  • buy_entries.venue already exists (always 'jupiter' today). It will hold the venue id that filled.
  • New: sells.venue (one migration, default 'jupiter_v1' for old rows).
  • New: venue_quotes sample log (venue, mint, size bucket, tokens out, ms, won). It powers the comparison chip, the admin venue card and future routing decisions. No user ids.
  • Quote payloads carry the chosen venue per row, so the buy step builds on the venue the user saw.

API and data changes

  • BuyOption gains route: { venue, label, kind, bestOf, deltaBps } and routes: RouteQuote[] (each venue's tokens out, cost, quote ms, ok).
  • POST /buys and POST /sells accept an optional venues: { [jarId or assetId]: VenueId }, checked against the venues offered in that review, the same way tokens is checked today.
  • New error ROUTE_CHANGED (added to the shared error list first) drives the Route changed sheet.
  • New env: JUPITER_API_KEY, DFLOW_API_KEY, VENUE_JUPITER_V2, VENUE_DFLOW, VENUE_JUPITER_RFQ, VENUE_QUOTE_BUDGET_MS (default 1500).
  • Rules gain routing: 'best' | VenueId and disabledVenues: VenueId[].
  • One migration: sells.venue, the venue_quotes table and the two rules columns. No backfill needed: existing buys already say 'jupiter'.

Before building

  • You: create a Jupiter developer account and API key (the free key allows 1 request a second, too few once several venues quote; the Developer plan allows 10).
  • You: request a DFlow production key through their form (2–5 days).
  • Test first: a $1 live buy on Jupiter /build with both our relay as payer and our platform fee, since the docs don't confirm the two together.
  • Unknown: whether DFlow handles Token-2022 xStocks; its docs don't say. Quote 20 xStocks before enabling.
  • Unknown: whether any RFQ market makers quote tokenized stocks at our order sizes.
  • Unknown: OKX's current developer docs and terms.
